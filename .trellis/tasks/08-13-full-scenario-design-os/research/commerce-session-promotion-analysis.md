# Commerce session promotion analysis

## Evidence boundary

This review sampled the active Codex task
`019ff53b-2ad8-7052-a50f-77a8d2da467e` on 2026-08-13 and inspected its current
Commerce benchmark, rehearsal and competition Host artifacts. The other task is

shipped capability or edit the Commerce implementation.

## What the Commerce workload actually stresses

The workload is useful because success is not one attractive image. One run must
preserve source truth while producing a closed family of localized text, main and
detail images, video and strategy evidence under exact policy, budget, filename
and Host constraints. Recent work exposed failures that mock execution did not:

- a model route can be locally effective but absent from the deployment Host's
  allowlist;
- a requested dimension can differ from the returned artifact's decoded
  dimension, so receipts must describe observed bytes rather than intent;
- a technically playable video can still fail product identity;
- one generated artifact cannot be used as proof for several semantic roles;
- a real receipt without retained bytes, semantic role closure and independently
  rerunnable verification is insufficient evidence;
- a seed or other deterministic parameter can be valid in Cutout's type but
  outside a Provider's exact numeric domain;
- aggregate engineering maturity and competition outcome quality answer different
  questions and cannot be collapsed into one score.

These are not Commerce-only accidents. They reveal general Design OS laws.

## Patterns promoted to the Design OS

### 1. Declared Outcome closure

Every Outcome Contract must state the required semantic roles, cardinalities,
constraints and dependency relations before execution. Readiness is computed
from the complete closure, never from a representative artifact.

The closure differs by Profile: Commerce currently has eleven delivery roles; a
UI suite has routes/pages/states; a Game Asset family has actions/directions/
frames/maps; Temporal has shots/tracks/variants. The Kernel needs only the typed
closure and hard-gate semantics, not those domain names.

### 2. Identity locks are executable invariants

A product, brand, character or design-system identity is not descriptive
metadata. Each derived node must bind the exact accepted identity/evidence
revision it consumes. Evaluators compare the produced artifact against that
anchor, and a failing derivative is repaired without invalidating valid siblings.

The Commerce image-to-video path is the first strong proof: technical playback
and subject fidelity are independent gates. Game Asset should reuse the pattern
for cross-action character consistency; UI should reuse it for token/component
identity; Temporal should reuse it for continuity.

### 3. Observed evidence outranks requested intent

Plans and capability requests record intended parameters. Receipts and artifact
records report the actual route, parameters, media type, dimensions, duration,
hash and validation result observed from bytes. Evaluation and delivery use the
observed record. A Host must never claim the requested shape when the artifact
decodes differently.

### 4. Repair is scoped to the failed graph node

Validation findings identify exact nodes, artifact revisions and evidence. A
repair plan retains accepted sibling hashes, spends only within the failed
closure and produces a successor candidate. This is the general alternative to
rerunning an opaque scenario pipeline.

### 5. Host parity is semantic, not byte-identical

Desktop and benchmark Hosts may have different authorization, route and target
bindings. After erasing only those declared Host bindings, the same fixture must
retain Outcome roles, dependencies, locks, lifecycle, evaluator gates and repair
boundaries. A capability gap is an explicit blocked node, not a rewritten graph.

### 6. Benchmark has two orthogonal planes

The Design OS evidence benchmark answers whether a Profile is trustworthy:
`contract -> conformance -> real-host -> production-rehearsal`. A Profile-owned
Outcome scorecard answers how good the delivered result is under one frozen
domain ruler. Neither can grant the other's success.

A competition score cannot make an unverifiable Host production-ready. Complete
Host evidence cannot prove that a generated campaign, sprite family or interface
is good. Both reports are derived from retained evidence; neither accepts
caller-authored totals or readiness.

### 7. Improvements need promotion packets

Every discovered improvement carries a reproducible fixture/run, evidence delta,
ownership classification and regression proof. Host constraints stay in the
Host. Domain policy stays in the Profile. Kernel promotion requires the same
invariant to be demonstrated by at least two distinct Profiles or one Profile
plus the held-out synthetic conformance Profile.

## Patterns deliberately not promoted

The following remain Commerce or Qianwen competition bindings:

- three locales, exact title/copy/catalog rules and the current eleven Commerce
  semantic roles;
- fixed physical filenames and A1-A7 competition weights;
- `qwen-image-3.0-pro`, `wan2.7-i2v-2026-04-25` and the competition model/origin
  allowlist;
- Debian 12, Node 22, ZIP size, evaluator entrypoint and unattended benchmark
  authorization;
- fashion-specific category/attribute maps, claims policy and product-image
  rubrics;
- any score optimization that has no reusable failure fixture outside the
  competition Host.

These constraints may be excellent stress fixtures. They do not define the
Kernel, global Workbench or public Agent surface.

## Consequences for the current program

- The Profile Platform must admit a typed required-role closure and identity/
  continuity lock semantics without learning Commerce role names.
- Profile manifests need separate adapters for evidence maturity and domain
  Outcome scoring; both adapters decode owning evidence before projection.
- Game Asset conformance should include one failed-frame repair that preserves
  accepted sibling frames and one identity-lock change that stales only dependent
  actions/maps.
- Cross-Host conformance must compare canonical semantics after declared binding
  normalization and fail when a Host silently deletes an unsupported Outcome.
- The Workbench Review and Deliver lenses should show completeness, identity and
  quality blockers separately from execution status.
- Public capabilities remain unchanged until executable Host behavior and the
  full Agent contract are synchronized and validated.
