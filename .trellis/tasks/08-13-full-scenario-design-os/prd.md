# Full-scenario Design OS

## Goal

Make Cutout the operating system for designed outcomes across product/UI,
brand, marketing, commerce, packaging, games, motion/media and future spatial or
physical domains.

"Full-scenario" does not mean placing every professional editor inside Cutout.
It means any legitimate design scenario can enter the same trustworthy loop,
share evidence and identity, use the right specialized capabilities, remain
reviewable and repairable, and leave as a verified deliverable without changing
the Kernel's meaning.

## First-Principles Definition

A design system exists to transform evidence, intent and constraints into a
human-experienced artifact or system. Media types and industries vary, but the
irreducible loop does not:

```text
understand -> contract -> plan -> authorize -> execute -> evaluate
           -> compare/decide -> repair -> approve -> deliver -> evolve
```

Therefore Cutout's universal product is not a universal drawing primitive. It is
the durable coordination and authority model around design work:

- evidence and rights;
- goals, audiences, unknowns and constraints;
- typed Outcomes and dependencies;
- candidates, decisions and locks;
- capability-aware execution;
- artifacts, provenance and evaluation;
- semantic changes, review and approval;
- delivery manifests, receipts and later impact.

Domain-specific geometry, time, interaction, physics, copy, policy and engine
semantics remain in typed Profile IRs. A single mega-IR would either lose meaning
or become an unmaintainable union of every domain.

## Confirmed Facts

- The implemented Design OS Kernel already owns versioned evidence/outcome/
  artifact graphs, frozen authority, scheduling, budgets, replay, impact and
  cross-profile promotion rules.
- Commerce already demonstrates a removable Profile with its own schemas,
  semantic roles, policies, recipes, evaluator and benchmark projection.
- Current Commerce real-Host work demonstrates that signed execution alone is
  insufficient: production proof also needs exact semantic-role closure,
  retained/decoded bytes, identity QA and a re-verifiable rehearsal bundle.
- Existing project plans already define semantic ChangeSets, a stable
  Brief/Sources/Board/Review/Deliver workbench, a horizontal media Timeline and
  truthful Host capability boundaries.
- The current desktop still exposes prototype-shaped coupling: the legacy
  Outcome/material runtime contains a closed union of material kinds and
  `IntentWorkspace.tsx` remains a roughly 10,000-line scenario orchestrator.
- The current one-subject `asset-production-plan.v1` cannot represent game
  animation families or layered maps without breaking its existing meaning.
- Cutout publicly declares no arbitrary paths, web search, cloud collaboration,
  general video-processing pipeline, or public engine exporter. A plan cannot
  represent these as shipped capabilities.

## Product Invariants

### I1. Outcome, not scenario, is the unit of the OS

- A Project may contain several related Outcomes from different Profiles.
- Outcomes share evidence, identity locks, libraries and policies through exact
  graph dependencies while retaining independent review and delivery state.
- "Website", "campaign", "sprite", "package" and "video" are useful Profile
  vocabulary, never Kernel states or global application modes.

### I2. Universality is open-world and typed

- The Kernel stays closed to domain names and open to versioned schemas.
- A Profile contributes schemas, graph fragments, recipes, policies, evaluators,
  presentation bindings, semantic actions and delivery descriptions.
- Domain IRs are plural and composable. Shared identity, artifact, provenance,
  command, approval and delivery relations connect them without pretending they
  are losslessly interchangeable.

### I3. Scene Extension Law

A new design scenario is admitted only when it can be added by:

1. a declarative, content-addressed Profile closure;
2. domain-owned typed IR and evaluators;
3. references to registered renderers, semantic actions and delivery adapters;
4. exact Host capability requirements and truthful unavailable states;
5. conformance and benchmark fixtures.

It must not require a scenario branch in Kernel reducers/scheduling/authority,
global navigation, approval semantics, history semantics or capability policy.
One catalog/registry installation entry is allowed; domain logic in that entry is
not.

### I4. Models propose; deterministic systems govern

- Models interpret open-ended evidence, propose Outcomes/candidates and perform
  attributed reviews.
- Deterministic code owns schemas, policy, dependency impact, budgets, authority,
  state transitions, measurable QA and delivery readiness.
- Run completion, a model's confidence, or the existence of bytes never implies
  artifact acceptance, Outcome approval or delivery approval.

### I5. Cutout is the control plane and semantic workbench

- Cutout natively owns brief formation, orchestration, visual/semantic comparison,
  dependency-aware review, high-value semantic edits, change management and
  delivery closure.
- It provides Board, Timeline and structured inspectors for cross-scenario work,
  but does not reimplement every low-level vector, 3D, audio, NLE, CAD, DTP or
  game-engine editing operation.
- Specialist tools are bounded sources, capability adapters or delivery targets.
  Their receipts return to the same Project history.

### I6. Neutral authority precedes target-specific projection

- Authoritative outcomes use the richest runtime-neutral domain contract that
  preserves intent and can support more than one target.
- Godot, Unity, web, print, marketplace and social-channel outputs are explicit
  projections over accepted revisions, not alternate sources of truth.
- Preview precedes approved apply; delivery cannot choose arbitrary paths,
  origins, tools or approval.

### I7. One workbench, several lenses

- Brief, Sources, Board, Review and Deliver remain stable global locations.
- Artifact schema and selected Outcome choose contextual renderers, inspectors
  and actions. Profiles do not add top-level navigation or separate applications.
- Designer and Builder lenses expose different density and language over the same
  commands, ChangeSets, authority and history.
- Unknown or unavailable artifact schemas render a safe diagnostic/read-only
  fallback rather than disappearing or being coerced into a known type.

### I8. Honest maturity is part of the product

- "Supported" requires contract, conformance, real Host and production rehearsal
  evidence appropriate to the Profile.
- Evidence maturity and Outcome quality are separate reports. A trustworthy Host
  cannot make a poor design good, and a high domain or competition score cannot
  make untraceable execution production-ready.
- Missing capability is `blocked`, not partial success and not a prompt fallback.
- A Profile can be installed, disabled, upgraded or removed without corrupting
  other Profiles or making historical artifacts unreadable.
- Public Agent surfaces change only when CLI, MCP, protocol, manifest, docs and
  executable Host behavior are synchronized and `pnpm agent:validate` passes.

### I9. Completeness and identity are declared before execution

- Each Outcome Contract declares its required semantic roles, cardinalities,
  constraints and dependencies. Readiness requires the exact closure, not one
  representative artifact or a successful Run status.
- Identity/continuity locks bind exact accepted evidence or artifact revisions to
  every derivative. Technical validity and identity fidelity are independent
  gates.
- Receipts report observed bytes and effective parameters. Requested dimensions,
  duration, route or format never override decoded output facts.
- Repair targets the failed node and dependent closure while preserving valid
  sibling hashes and receipts.

## Reference Scenario Proof

The architecture must be proven by orthogonal workloads, not feature count:

| Reference | Stress introduced | Shared OS behavior |
| --- | --- | --- |
| Product/UI prototype | interactive structure, routes, components, code delivery | evidence, candidates, graph, review, delivery |
| Commerce/brand campaign | facts, localization, policy, image/video/document roles | same lifecycle, locks, repair, receipts |
| Game asset production | multi-action identity, frame geometry, layers, collision, engine-neutral bundle | same graph, candidate decisions, QA, targeted repair |
| Temporal media | ranges, takes, continuity, audio/captions, variants | same commands, revisions, approval and delivery |

Prototype/UI and Commerce establish the base; Game Asset is the third-profile
extension proof; Temporal proves that time is a horizontal dimension rather than
a separate product.

## Acceptance Criteria

- [ ] F1: A universal brief can propose a mixed Project with UI, commerce,
      game-asset and temporal Outcomes without asking the user to select internal
      Profile taxonomy first.
- [ ] F2: Prototype/UI, Commerce and Game Asset compile through the same Kernel
      records, lifecycle, authority, repair and delivery gates.
- [ ] F3: Adding/removing the Game Asset Profile changes no Kernel reducer,
      scheduler, authority rule, approval lattice, history rule or global
      navigation branch; a conformance audit enforces this extension law.
- [ ] F4: One Project shares a brand/identity lock and evidence across at least
      three Profiles while each Outcome retains independent revision, candidate,
      evaluation, approval and delivery state.
- [ ] F5: Changing shared evidence or a lock produces an exact ImpactSet and
      stales only dependent nodes across Profiles; accepted unrelated hashes stay
      unchanged and no Provider call starts during propagation.
- [ ] F6: The Workbench selects registered renderers/inspectors/actions by typed
      artifact/Outcome schemas, supports mixed Board/Timeline content, and safely
      diagnoses unknown or disabled Profile content.
- [ ] F7: Equivalent Designer, Builder and Agent actions resolve to the same
      semantic commands, ChangeSets, authorization, conflicts and history.
- [ ] F8: Profile installation, version locking, upgrade, disable and removal are
      previewed, content-addressed and reversible; historical records remain
      inspectable and unsupported required schemas fail without mutation.
- [ ] F9: Missing Host capabilities block exact nodes and explain alternatives
      without weakening policy, inventing tools or falsely satisfying Outcomes.
- [ ] F10: Runtime-neutral Game Asset output and temporal/domain IRs precede
      target adapters; managed exporter failure cannot alter accepted artifacts.
- [ ] F11: The Profile-neutral evidence benchmark reports per-Profile contract,
      conformance, real-Host and rehearsal maturity while a separate Profile-owned
      Outcome scorecard reports domain quality under a frozen ruler; neither can
      mint the other's readiness, and critical regressions remain release blockers.
- [ ] F12: Existing prototype `.cutout` state, accepted bytes, hashes, recovery,
      approvals and exports remain compatible throughout incremental migration.
- [ ] F13: Scale fixtures prove graph composition, impact, workbench projection
      and history operate on indexed affected closures under declared budgets.
- [ ] F14: Every implemented public Agent-surface addition synchronizes CLI, MCP,
      protocol, manifest, docs and generated plugin runtime and passes
      `pnpm agent:validate` plus affected checks.
- [ ] F15: UI, Commerce and Game Asset each declare an exact required-role
      closure; missing/duplicated roles block readiness, and a failed child node
      can be repaired without changing accepted sibling hashes.
- [ ] F16: Desktop and bounded benchmark Hosts pass one canonical semantic-parity
      fixture after erasing only declared Host bindings; unsupported capabilities
      remain explicit blocked nodes rather than disappearing or changing meaning.
- [ ] F17: A shared identity-lock fixture propagates from accepted source evidence
      into Commerce image/video, UI design-system and Game Asset action outputs;
      every derivative reports identity fidelity independently of byte validity.

## Out Of Scope

- General office/business automation, arbitrary coding/shell, unrestricted web
  or computer use, or domains whose primary outcome is not designed.
- Rebuilding every specialist editor or claiming lossless interchange between
  unrelated domain IRs.
- Cloud collaboration, live Figma sync, arbitrary engine-project mutation or
  any Provider/target capability without real Host evidence.
- Declaring all scenarios production-ready at once. The architecture is
  open-world; each Profile earns its own maturity evidence.

## Product Direction

Cutout will optimize for a **design control plane plus semantic workbench**. It
will own intent, evidence, identity, orchestration, decision, repair, approval and
delivery truth while composing bounded specialist capabilities. Full-scenario
coverage will not be measured by how many low-level editors Cutout reimplements.
